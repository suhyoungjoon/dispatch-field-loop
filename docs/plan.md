# 기획: 실적 시뮬레이션과 현장 의견 대화

## 1. 배경

코어 레포(`optimization-agent-harness`)는 규칙 엔진의 **배정 계획**을 AI가 분석하고 개선안을 내고, 코드가 시뮬레이션하고, 사람이 승인하는 흐름까지 구현했다. 실제 API 실험 결과는 코어 레포의 `docs/experiment-real-api-2026-10.md`에 있다.

남은 두 빈칸이 있다.

1. **실적이 없다.** 지금 지표는 모두 계획 기준이다.
   - 계획을 현실에 적용했을 때 무슨 일이 생기는지 알 수 없다. 고객이 시간 변경을 받아들였는지, 늦게 도착했는지, 취소했는지 같은 것이다.
   - 고객은 희망 날짜·시간을 가장 중요하게 여긴다. 그래서 배정을 늘리려고 시간을 옮기는 개선안의 실제 비용을 판단할 근거가 없다.
   - 현재 엔진은 실패 건을 다음 날로 넘기지 않아, 희망 날짜가 밀리는 상황도 모델에 없다.
2. **현장 의견이 들어올 통로가 없다.** 실험에서 결과를 가장 크게 바꾼 것은 사람의 판단이었다. 예를 들어 "관할 밖 4km 넘으면 출동 불가", "정시 손실은 3%p까지" 같은 것이다. 이것을 대화로 끌어내 구조화하는 기능이 필요하다. 코어 레포 plan.md 15장 M12의 "별도 레포: 현장 의견 대화" 항목을 이 레포가 맡는다.

## 2. 목표

- 배정 계획을 받아 **가상 실적**을 만드는 시뮬레이터를 만든다. 개선안의 득실을 고객 결과(완료·불만·일정 재요청·취소·날짜 이월)로 비교할 수 있게 한다.
- 현장 담당자와의 **대화로 제약·사실·발견 판정을 구조화**하고, 코어의 제약 형식으로 개선 흐름에 넣는다.
- 두 가지를 하나의 흐름으로 잇는다.

> 계획 → 실적 → 분석 → 현장 대화 → 개선안(제약 반영) → 전후 시뮬레이션(계획 + 실적) → 사람 승인

## 3. 실적 시뮬레이터 설계

### 3.1 세상 설정 (AI에게 숨김, 정답표 역할)

| 구성 | 내용 | 심어 둘 정답 (초안) |
|---|---|---|
| 고객 반응 | 희망 시각과 배정 시각의 차이에 따라 수락 / 불만 / 일정 재요청 / 취소를 확률로 정한다. 작업 유형·건물 유형마다 허용 폭이 다르다 | **P5**: 장애 고객은 30분만 늦어도 불만이 급증한다 (개통은 ±60분까지 대체로 수락) |
| 날짜 이월 | 배정 실패 건은 다음 날로 넘어가 우선 배정된다. 하루 밀릴 때마다 불만·취소 확률이 오른다 | 이틀 넘게 밀리면 취소 |
| 실행 편차 | 실제 작업 시간과 이동 시간이 추정값과 다르다. 늦으면 뒤 일정이 연쇄로 밀려 도착 지연이 생긴다 | **P6**: 승주 작업은 실제로 추정보다 25% 길다. 출퇴근 시간대 이동이 느리다 |

- 세상 프로필을 3개(관대 / 보통 / 민감) 둔다. 결론이 프로필에 따라 뒤집히는지 확인하는 데 쓴다.
- 같은 계획·같은 실적 seed면 같은 실적이 나온다. 개선 전후 비교에는 같은 seed를 쓴다(공통 난수).

### 3.2 실적 레코드와 지표

- 레코드는 지시서 하나마다 남긴다. 담을 내용: 실제 시작 시각, 도착 지연, 실제 소요, 고객 결과, 이월 일수.
- 지표:
  - 약속 준수율: 희망 날짜·허용 시간 안에 완료한 비율
  - 불만율, 취소율
  - 평균·상위 10% 도착 지연
  - 평균 이월 일수
  - 추정 대비 실제 소요 비율 (작업 유형·난이도별)

### 3.3 분석·개선과의 연결

- 분석 agent에 실적 집계 도구를 준다. 예: 구간별 불만율, 작업 유형별 실제/추정 소요 비율.
  - 코어의 `analyze`가 외부 도구를 받을 수 있는지 먼저 확인한다. 받을 수 없으면 코어 변경을 요청한다(우회 금지).
- **추정값 보정 경로:** 코어 레포 M13에서 개선안이 추정값(`estimate`)을 바꾸지 못하도록 막을 예정이다. 이 레포는 별도의 "추정값 보정 제안" 경로를 만든다.
  - 실적 집계가 근거로 붙어야 한다.
  - 사람이 승인해야 반영된다.
  - 예: "승주 작업 실적이 추정보다 평균 25% 김 → 승주 가중치 1.5 → 1.9".
- 득실 비교: 개선안마다 계획 지표와 실적 지표를 함께 보여 준다. 예: "배정은 +134건이지만 그중 고객이 받아들인 건은 몇 건인가".

## 4. 현장 의견 대화 설계

(코어 레포 plan.md 15장 M12 "별도 레포" 항목을 이어받는다.)

| 구분 | 내용 |
|---|---|
| 입력 | 분석 리포트, 현재 파라미터(분류 포함), 개선안과 시뮬레이션 결과(계획 + 실적) |
| 도구 | 리포트·발견 조회, 실적 집계 조회, `simulate_params`, 제출용 `record_notes` |
| 확인 방식 | 정리할 항목이 생기면 "이렇게 이해했습니다"로 확인을 받는다. 수치는 도구 결과에서만 인용한다(코어 근거 검사 재사용) |
| 구조화 항목 | **제약**(코어 제약 형식), **사실**(데이터에 없는 현장 정보), **확인 필요**(현장 의견과 데이터가 어긋나는 지점), **발견 판정**(코어 `labels` 형식). 항목마다 말한 사람, 시각, 근거, 상태(제안됨 → 사람 확인됨) |
| 반영 | 확인된 제약만 개선 agent에 넘긴다. 대화가 규칙을 직접 바꾸지 않는다 |

실적 시뮬레이터와 대화가 만나는 지점도 있다. 현장 의견("장애 고객은 30분 늦으면 민원이 들어온다")이 실적 데이터와 맞는지 대조해 "확인 필요" 항목으로 올린다.
